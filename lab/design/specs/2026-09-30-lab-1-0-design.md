## 1. Intent

Turn the lab from "a repo with a project in it" into **a world with countries**: the repo is Claude's and Tomas's working environment (the world); each project is an independent, fully documented country. At the same time, change how Claude works so that Tomas genuinely learns every step and Claude visibly improves over time.

**What Tomas asked for (retro):**
- Docs are scattered and the structure does not scale → simple, clear, no redundancy, traceable, explainable.
- Separate agent docs from project docs.
- Tutoring at every step: he finished pitwall without understanding the dbt logic, feature whys or code.
- Visible self-improvement of Claude's memory and way of working, every project.
- A private space for ideas (tech, projects, business — goal: found a company). The repo is public.
- Industry-standard tech; excellence; cost-aware; creative and differential.

**Guiding premise for Claude's own config:** highest possible quality while containing cost. Config files may grow when the cost-benefit justifies it; a rule that is not loaded is a rule that gets broken.

**Success criteria**
1. Every question about the lab has exactly one place where it is answered (table in §3).
2. `docs/` no longer exists; no Markdown link in the repo is broken.
3. A new project created with `new-project` v2 gets the new layout (`docs/guide.md`, `docs/design/`, `docs/decisions/`) and its tests pass out of the box.
4. A visitor understands the world/countries model from the root listing and `README.md` alone.
5. Claude, in a fresh session, loads every hard rule from `CLAUDE.md` and runs workflows (ship, release, verify-before-design) as skills rather than from recall.
6. Every logical block of work follows the tutoring protocol (§5), and each technology used ends up in a didactic vault note with concrete cases from our code.
7. Lessons change Claude's behaviour when they are detected, and each change is visible in `agent/CHANGELOG.md`.

## 2. Approach

**Option 1 — the world visible at the root** (chosen).

Rejected:
- *Everything under `docs/`* (`docs/lab/`, `docs/agent/`) — the GitHub convention and fewer moves, but it buries what makes this repo different: a portfolio visitor seeing *how an engineer works with an agent* at the root is part of the product.
- *Two repos* (agent environment vs projects) — breaks ADR 0001 (monorepo) and traceability between retros and projects.

Delivery: **one spec, two plans**, A (structure) then B (agent operating model), each with its own issue and PR. Plan B is written after A is merged. The lab releases **v1.0.0** after B.

**Decisions inside the layout**
- **No `agent/workflows/`.** Workflows *are* skills and Claude Code only loads them from `.claude/skills/`; `agent/README.md` links to them instead of duplicating.
- **CLAUDE.md keeps the rules; skills keep the procedures.** Anything Claude must never forget stays in `CLAUDE.md` (it may grow if needed). Step-by-step workflows move into skills; `lab/conventions.md` describes them for humans.
- **Private stays private.** Ideas and business live only in the vault; the public repo gets `lab/tech-radar.md`.
- Commit scopes: project name, `lab`, and new **`agent`** for changes to Claude's own system.

**Definition of Done (new):** tests green · `make lint` clean · project README · `docs/guide.md` · ADRs for durable decisions · tutor review done and vault notes enriched with the project's cases · issue closed via PR.

## 5. Plan B — agent operating model

**Tutoring protocol** (Tomas's choice), per logical block of 2–4 related tasks:
1. **Brief before** — 2–3 sentences: what, with which characteristics, in which tech, why; and where we are in the project. No approval wait.
2. **Execute without blocking.**
3. **Tutor review after** — Claude's reasoning as an elite engineer: why, how, alternatives, technical characteristics to keep in mind. No interview-style questions.
4. **Vault** — every technology or technique used becomes didactic knowledge with concrete cases from our code (how it works inside, why configured so, local vs production, problems hit and why, alternative techs). Enrich existing notes; notes evolve.

`agent/tutoring.md` holds the full protocol and the vault note standard with examples; `CLAUDE.md` holds the summary as a hard rule.

**Skills**
- `ship` — push → PR with `Closes #n` → CI green → `pr-reviewer` if non-trivial → fix Critical/Important → squash merge → verify the issue closed (close manually if not linked) → delete branch → update `dev`.
- `release` — the three release steps; always stops for Tomas's OK before the PR into `main` and before `gh release create`. *Amended in plan B:* the skill is user-invoked only (`disable-model-invocation`), so Tomas typing `/release` is the OK for the PR into `main`; it still stops before the public `gh release create`.
- `verify-before-design` — triggers before designing anything touching cloud accounts, auth, CI or versions. Checklist: real org/account, billing currency, supported auth modes, versions/tags that exist today (Context7 or official docs), quotas and free tier.

**World-status SessionStart hook** — current branch, open issues and PRs, last `pitwall-pipeline` run (status, date). Uses `gh` with a timeout, fails silently offline, has a test like `reviewer-bash-allowlist.test.sh`. Month cost is deferred to the Grafana observability project (needs billing export to BigQuery).

**Continuous self-improvement**
- `agent/lessons.md` — each lesson as symptom → cause → rule, seeded from pitwall: assumed instead of verified (org, EUR, setup-uv tag, Evidence auth); fragile Bash chaining; plans too long; `Closes #n` not always closing the issue; hidden browser pane pausing Observable.
- **Lessons are applied when detected, not at retros.** Claude changes its skill/hook/CLAUDE.md/memory right away, logs it in `lessons.md` + `agent/CHANGELOG.md`, and reverts freely if it does not work — this is trial and error. Memory changes are immediate; repo changes go through a small `agent`-scoped PR or ride the current branch when related. Retros review what changed.
- Memory consolidation: technical lessons move to `agent/lessons.md` (public, versioned); memory keeps preferences and state.
- Leaner plans: for repeated patterns, a plan references the earlier plan instead of rewriting all the code.

**Records** — `agent/retros/2026-09-30-pitwall.md`; `agent/CHANGELOG.md` entry for Lab 1.0.

**Close** — release v1.0.0 with Tomas's OK.
